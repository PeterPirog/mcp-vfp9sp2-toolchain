# Contributing

## The contract comes first

Development is governed by the frozen Source of Truth at
`spec/SOURCE_OF_TRUTH.md`. Every change maps to explicit `REQ-*` requirement
IDs; unexecuted verifiers are never allowed to report PASS. Repository
documentation never overrides the Source of Truth.

## Deterministic verification before any integration

```text
python tools/verify.py self-consistency
python tools/verify.py schemas
python tools/verify.py layout
python tools/verify.py determinism
python tools/verify.py package
python tools/verify.py no-download
python -m unittest discover -s tests -t .
```

All must pass (or fail closed with an explicit BLOCKED reason) before a
candidate is integrated.

## Rules that are enforced, not advisory

- **Generated artifacts are protected.** `spec/*.json` control-plane
  artifacts and `release-gates/*` are generated by
  `tools/generate_control_plane.py`. Never hand-edit them; change the
  generator or the Source of Truth (the latter only as explicit contract
  evolution) and regenerate.
- **Never weaken verification.** Deleting a failing test, broadening ignore
  rules, adding unconditional skips, or weakening assertions is prohibited.
- **Truthful capability state.** Unimplemented capabilities report
  NOT_IMPLEMENTED; placeholder success is forbidden.
- **Windows only.** Product semantics target Windows; non-Windows behavior
  is unsupported and must not consume test scope.
- **No private data.** Public fixtures use redistributable synthetic data
  only; never commit production/customer VFP data, credentials, or
  recovery-vault content.
- **Dependency discipline.** Dependency changes require an explicit
  requirement justification, approved origins, and a canonical lock update
  through the defined workflow; never float versions.
- **Authoring provenance.** Every candidate carries authoring provenance
  (MANUAL/AUTONOMOUS/HYBRID with actor attribution). Independent review must
  come from an execution that did not author the candidate.

## Pull requests

1. Bind the change to exact requirement IDs.
2. Include the verifier evidence for the affected requirements and the
   repository-wide deterministic quality gates.
3. State which release gate (if any) the change targets; release
   qualification follows the canonical release-gate manifests only.
